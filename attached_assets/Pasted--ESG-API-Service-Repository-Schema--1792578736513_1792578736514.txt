# 管理员端第一阶段修复：业务事实、ESG 中立性与数据边界

## 一、执行范围

本次只修复管理员端及其直接依赖的后端 API、Service、Repository、Schema 和相关测试。

明确不处理：
- 认证员端和客户端；
- ESG 自动评级或认证审核工作流；
- 四维加权算法、既有风险公式和风险等级规则的重写；
- 真实通知发送、真实收款、真实转账；
- 未定义的资金分配优化；
- 真实企业数据接入；
- 真实 AI API 调用。

使用合成演示数据、模拟 Transport 和内存 Repository 完成开发与测试。

## 二、开始修改前

1. 检查当前 Git 工作区，记录已有用户修改，不覆盖或回滚无关变更。
2. 复核此前盘点指出的文件和函数，确认问题仍然存在。
3. 先列出准备修改的文件、具体原因和预期测试。
4. 不访问、修改或清空共享业务数据库。
5. 不执行会修改共享工作区数据的端到端脚本。
6. 不调用真实 OpenAI、Gemini 或其他外部 AI 服务。

## 三、修复任务

### 任务 A：AI 调用前置校验

检查 `businessContext()`、`generateAdvice()` 及其上游编排。

在发送 AI 请求前，明确验证：
- 风险记录是否存在且属于当前计划版本；
- 客户和账单关联是否完整；
- 任务数量是否符合当前 Schema 和业务约束；
- 任务 ID 是否唯一；
- 账单金额、日期、币种及关联信息是否完整；
- 当前计划是否已过期或被更新版本替代；
- 当前状态是否允许生成建议。

缺少必要信息时，应返回稳定、可识别的 reasonCode 和可解释错误，不使用非空断言将问题拖到深层逻辑。

对于明确不允许生成建议的情况，必须在 Transport 调用之前终止，并以模拟 Transport 的调用计数证明没有发出请求。

不要擅自修改现有业务阈值或任务数量上限。

### 任务 B：保护业务事实

检查 `ai-provider.ts`、`ai-schema.ts`、`communication.ts` 和 `service.applyAdvice()`。

AI 可以提供风险解释、协商策略和沟通措辞，但不能成为财务事实的权威来源。

优先使用现有权威数据或服务端模板提供：
- 账单金额；
- 到期日和逾期天数；
- 当前审批状态；
- 已批准的延期条件；
- 其他会影响客户实际义务的业务事实。

对 AI 输出中的事实进行适当校验。对于无法可靠校验的关键承诺，不要直接接受为可执行话术；应拒绝相应输出或回退到安全模板。

特别注意：不能只检查 JSON 结构、任务 ID 和字段类型，就将正文视为事实正确。

不得让 AI 修改风险分数、评分权重、金额、优先级、排序、审批状态或模拟执行状态。

### 任务 C：保护未知 ESG 的中立性

当前 ESG 信息只允许来自已有业务记录和既有审核结果。不得在本次任务中新增自动 ESG 评级。

检查所有 AI 可变文本字段，包括：
- 风险解释；
- 风险归因；
- 催收策略；
- 英文和马来文沟通草稿；
- ESG 考量字段。

当 ESG 状态未知、缺失、未审核或无法确认时：
- 不得将其描述为客户 ESG 表现差；
- 不得据此增加客户风险等级或改变催收排序；
- 不得将“没有认证信息”推断为“不符合 ESG”；
- 不得在对外通知中引入未经证实的 ESG 负面指控。

当现有审核结果明确时，也只能准确引用已有记录，不得超出记录作推断。

对结构合法但包含负面未知 ESG 推断的模拟响应进行测试。不能仅依赖 Prompt 文字约束；应有服务端校验、受控模板或其他可验证机制。

### 任务 D：明确合成 CSV 输入边界

检查 `receivables.tsx`、`csv.ts`、`service.importData()` 及其相关契约。

在管理员端导入入口清楚说明：当前环境是合成数据演示环境，导入文件必须符合项目定义的演示数据要求。

必要时增加显式确认，并保留来源元数据。确认机制只能表明用户确认其输入符合演示要求，不能宣称系统已验证数据真实来源。

不得将未经验证的 CSV 自动标记为已验证的合成数据。不得把来源标记当成真实的数据鉴别机制。

继续保留已有金额精度、日期、重复记录、关联完整性和整批原子导入保护。

不要擅自删除原有演示数据或执行导入操作。

## 四、必须新增或补充的无费用测试

使用模拟 Transport、内存 Repository 和合成数据，覆盖：

1. 缺少风险记录、客户或账单关联时，不发送 AI 请求。
2. 空任务、重复任务 ID 和过期计划得到明确处理。
3. AI 返回结构合法但金额错误的内容时，不能直接作为有效建议应用。
4. AI 返回错误日期或未经批准的延期承诺时，不能直接成为可执行话术。
5. ESG 未知时，负面 ESG 推断不能进入最终有效建议。
6. ESG 未知时，其他文本字段也不能绕过中立性约束。
7. 缺少 ESG 记录不会被当作负面风险证据。
8. 合成 CSV 输入说明和来源元数据符合预期。
9. 导入失败时不留下部分数据。
10. 原有审批、拒绝、版本替代、过期阻断及模拟执行门禁仍然通过。

如果现有架构无法可靠验证某个文本事实，请明确记录剩余风险，不得通过放宽 Schema 或跳过校验让测试通过。

## 五、执行与验收要求

完成修改后：
1. 运行相关的无费用单元测试。
2. 运行现有相关 workflow 回归测试前，先检查测试是否会写入共享数据；如会，改用内存替身或隔离测试环境。
3. 执行类型检查、相关包构建及 `git diff --check`。
4. 不运行真实 AI 验收命令。
5. 不修改认证员端、客户端或无关 UI。
6. 不将测试源码中的断言描述为实际测试通过。

最终报告必须包含：
- 修改文件清单及每个文件的修改目的；
- 新增测试清单和实际执行结果；
- 未解决的问题与剩余风险；
- 对四维算法、审批门禁和模拟执行未被破坏的回归证据；
- 明确声明是否调用了真实 AI、是否访问或修改了共享业务数据库。

如果测试失败，先定位和报告失败原因，不得删除测试或降低安全要求来追求通过率。
