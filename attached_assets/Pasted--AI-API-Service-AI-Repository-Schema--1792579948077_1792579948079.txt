# 管理员端第二阶段：跨进程 AI 去重与建议版本审计

## 一、工作范围

仅处理管理员端及其直接依赖的 API、Service、AI 编排、Repository、数据库 Schema、审计契约和测试。

不开发认证员端或客户端，不重写风险算法、四维评分、审批状态机、通知模板或模拟执行逻辑。

本阶段不调用真实 AI，不修改 Secret，不导入数据，不重置工作区，不执行审批或模拟执行，不直接修改共享业务数据库中的业务记录。

开始前先检查 Git 工作区与第一阶段改动，保留所有现有修改。

## 二、任务 A：跨进程 AI 调用去重

先阅读现有 `ai-generation.ts`、`ai-enrichment.ts`、Repository 事务实现及 `demo-workspaces` 相关 Schema，提出最小实现方案，再修改代码。

### 必须满足

1. 去重键必须准确关联工作区、计划或风险事件、计划版本及生成任务类型，不能把不同版本误判为同一请求。
2. 两个独立服务实例同时请求同一版本时，只允许一个实例取得有效的生成权。
3. 去重协调必须跨进程生效，不能仅依赖进程内 Map。
4. 必须定义生成中、成功、失败、超时、进程中断及租约过期的处理规则。
5. 失败后允许按照明确的状态转换再次生成；不能留下永久无法恢复的占位记录。
6. 旧版本响应迟到时，不得覆盖已修改、已批准、已拒绝、已延后或已被新版本替代的计划。
7. 保留现有的规则回退行为和人工审批门禁。
8. 不要为了减少重复请求而错误复用不匹配版本的 AI 输出。
9. 不改变四维评分、风险等级、任务金额、优先级、排序或审批状态。
10. 明确区分“避免重复请求”和“保证绝对只调用一次”。网络中断或进程崩溃可能发生在供应商已接收请求、但本地尚未记录结果的窗口；如果现有系统无法消除这个窗口，必须如实记录限制。

### 测试要求

使用两个独立编排实例、共享的内存协调实现或专门的隔离测试替身模拟并发。

至少覆盖：
- 两实例同时请求相同计划版本；
- 两实例请求不同计划版本；
- 一个实例失败后另一个实例能否按规则接管；
- 租约过期与旧执行者迟到；
- 新版本已生成后旧版本响应返回；
- 已审批或已替代计划拒绝应用旧响应；
- 异常退出后占位能够恢复；
- 规则回退和现有审批门禁不变。

不要仅通过在单个实例中调用两次函数来声称完成跨进程并发验证。

如果生产实现需要数据库唯一约束、事务或迁移，先说明具体变化和回滚方法，并通过隔离测试验证；未经授权不得对共享数据库执行迁移或写入。

## 三、任务 B：AI 建议与受控模板的不可变审计快照

检查现有 AI 生成、规则回退、受控模板、人工修改、审批及审计记录。

为每次生成尝试建立可追溯记录，并将以下内容分开保存：

1. 原始 AI 返回结果（仅在允许、安全且符合数据保留规则时保存）；
2. 服务端校验后的 AI 建议；
3. 因业务事实或 ESG 约束而被替换的受控模板；
4. 当前最终拟执行通知；
5. 人工编辑后的版本；
6. 审批决定及其对应版本；
7. 生成失败、被拒绝或被旧版本丢弃的结果。

每条快照至少应有：
- 唯一记录 ID；
- 工作区和计划／任务标识；
- 计划版本及生成尝试 ID；
- 创建时间；
- provider 与来源标识；
- 处理状态及稳定 reasonCode；
- 内容策略标识或版本；
- 内容校验结果；
- 与前后版本的明确关系。

### 数据安全与审计边界

- 快照必须不可变；编辑应创建新版本，不覆盖原记录。
- 不保存 API Key、Secret、认证头或不必要的原始异常内容。
- 不得把 `rules_fallback` 记录显示为真实 AI 生成成功。
- 不得把人工修改后的内容冒充为原始 AI 输出。
- 对已经被拒绝或丢弃的迟到结果，保留必要的审计元数据，但不能把它应用到当前计划。
- 不要为“审计完整”而无条件保存不受控制的原始文本；先评估现有数据保留、访问权限和敏感信息风险。
- 保留旧 Gemini、旧直连 OpenAI 与托管 OpenAI 的历史来源，不批量改写旧记录。

### 测试要求

至少验证：
- AI 成功生成后可以还原当时的建议；
- 规则回退可还原当时使用的受控模板及来源；
- 人工修改后原始建议不变；
- 延后、重算或新版本生成后旧快照仍可查询；
- 被拒绝、失败及迟到的响应不会显示为成功应用；
- 审批记录准确指向获批的计划版本；
- 敏感密钥与认证信息不会进入快照；
- 快照关联不存在时能安全报错，不产生误导性的成功记录。

## 四、测试与验收

1. 优先使用内存 Repository 和模拟 Transport。
2. 对数据库唯一约束、事务及租约语义使用隔离测试环境，不连接共享业务数据库。
3. 运行相关单元测试、并发测试、现有 workflow 回归、类型检查、构建和 `git diff --check`。
4. 运行任何可能启动 Web 服务或读取工作区的测试前，先说明它是否会发起 `/api/workspace` 请求或访问数据库。
5. 不调用真实 AI，不执行真实通知、付款或收款。
6. 不删除原有测试，不降低原有校验标准以追求测试通过。

最终报告必须说明：
- 实际修改文件与 Schema／迁移变化；
- 两个独立实例的并发测试如何构造；
- 实际测试数量与结果；
- 去重机制仍无法保证的边界；
- 审计快照保存了哪些内容、如何区分原始建议和最终通知；
- 是否访问或修改了共享数据库；
- 是否调用了真实 AI。

如果某项测试无法在隔离环境完成，必须明确标注未验证，不得以代码审查代替测试通过。
