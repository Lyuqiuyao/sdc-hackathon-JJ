# 项目范围收敛：仅保留管理员端，并完善 AI 审计能力

## 一、项目最终目标

本项目只需要一个管理员端（管理员／商家财务管理端）。

认证员端和客户端不再属于项目范围。请逐步清理相关页面、路由、导航入口、角色切换、专用 API 和不再使用的代码，最终只保留管理员端。

管理员端需要完整支持：
- 管理员演示登录与工作台；
- 应收账单及客户信息；
- 现有 ESG 记录与审核结果的只读展示；
- 风险检查及风险概览；
- 确定性风险计算、四维加权评分、优先级及排程；
- AI 风险解释、催收策略及双语沟通建议；
- 规则回退与明确的状态提示；
- 人工编辑、审批、拒绝、延后和重新计算；
- 模拟执行及结果；
- 审计日志、AI 建议快照与版本追踪；
- Provider 状态和错误反馈。

## 二、重要业务边界

1. 风险等级和四维加权分数由现有确定性业务算法计算，不能迁回 LLM。
2. AI 只能提供解释、策略及建议话术，不得修改金额、权重、分数、风险等级、任务排序、审批状态或执行状态。
3. ESG 只能读取现有业务记录和审核结果。不得新增 AI 自动评级或自动认证。
4. ESG 未知、缺失或未审核时，不得推断客户存在负面 ESG 风险。
5. 任何对外通知都必须遵守现有业务事实和服务端安全模板约束。
6. 审批与模拟执行必须分开。未经批准的方案不得执行。
7. 当前执行只用于演示，不真实发送通知、不收款、不转账、不修改真实付款数据。
8. 当前使用合成演示数据，不接入真实企业数据。
9. 不重写已通过测试的风险公式、四维算法、审批状态机、跨实例生成权协调和快照保护，除非发现具体缺陷并先说明理由。

## 三、第一部分：只保留管理员端

### 第一步：只读盘点

先检查整个工作区，识别：
- 前端应用和路由；
- 页面与导航；
- 登录、角色切换及权限判断；
- API 路由与生成的 API Client；
- Service、Repository、Schema 和测试；
- 认证员端、客户端专用代码；
- 被多个端共同使用的组件或后端服务。

输出清单，逐项标记：
- 管理员端必须保留；
- 仅认证员端使用；
- 仅客户端使用；
- 多端共用，不能直接删除；
- 需要进一步确认。

特别检查管理员端是否依赖目前准备删除的共享组件、数据模型或 API。

本步骤不修改代码、不执行数据库写操作、不调用真实 AI。

### 第二步：制定最小清理方案

只删除明确不再使用的认证员端和客户端入口及专用代码。

要求：
- 管理员端入口和所有管理员功能必须保留；
- 不得因为移除两个端而删除管理员端所依赖的共享 Service、Repository、Schema、业务规则或 API；
- 清理角色切换和不再需要的导航入口；
- 不把隐藏导航菜单当作彻底移除；
- 检查直接 URL 访问、路由 fallback、API 权限和构建配置；
- 保留必要的管理员身份验证与工作区权限校验；
- 不执行共享数据库迁移或删除数据。

### 第三步：分批修改与验证

每批修改后运行相关类型检查、测试及构建。

验收标准：
1. 应用只呈现管理员端入口和管理员端导航。
2. 不存在可访问的认证员端或客户端页面入口。
3. 管理员端所有既有功能和 API 仍可使用。
4. 共享业务逻辑没有被误删。
5. 现有风险算法、四维评分、审批、版本保护、模拟执行和审计测试继续通过。
6. 不修改或清理历史 AI 来源记录。
7. 不执行真实 AI 调用。
8. 不访问或修改共享业务数据库中的业务记录。

如果发现删除某个模块会影响管理员端，先报告依赖关系，不得强行删除。

## 四、第二部分：明确并完善 AI 审计

当前设计不保存投影前的原始模型正文，但保存结构校验摘要及通过校验、安全投影后的内容。

请先检查当前实现，评估以下审计需求是否已满足。

### 必须可追溯的内容

每次 AI 生成或规则回退都应能够追溯：
- 请求尝试 ID；
- 工作区、计划、任务及对应版本；
- 使用的 Provider 与模型标识（能够可靠获取时）；
- 生成时间及处理状态；
- 校验结果和稳定 reasonCode；
- 哪些字段通过校验；
- 哪些字段被拒绝、删除、替换或使用受控模板；
- 最终采用的有效建议；
- 最终通知正文；
- 人工修改后的版本；
- 审批决定及精确关联的获批版本；
- 迟到响应、过期响应或未应用结果的处理结果。

### 原始模型响应的保存策略

先评估是否确实需要保存投影前的原始模型响应。

优先方案：
- 通过结构化诊断信息记录失败原因、字段级校验结果及模板替换原因；
- 不记录 Secret、认证头或无关敏感信息；
- 不把原始模型文本当作业务事实；
- 不让未经校验的原始响应出现在普通管理员通知界面。

如果当前需求确实需要保存原始响应：
1. 先提出单独的保存策略，包括访问权限、数据保留期限、敏感内容处理、容量影响和删除机制。
2. 仅在合成演示数据范围内评估和测试。
3. 将原始响应与校验后建议、受控模板、最终通知分开存储。
4. 任何后续修改都不得覆盖原始记录。
5. 不允许原始响应直接进入审批或模拟执行流程。
6. 不保存密钥、认证头、无关上下文或未经必要性评估的敏感信息。
7. 未经我明确确认，不要启用完整原始响应持久化。

### 管理员端审计界面

检查现有页面是否能清楚展示：
- AI 原始响应是否保存；
- AI 建议是否通过校验；
- 是否应用受控模板；
- 当前最终通知正文；
- 人工修改历史；
- 审批人、审批时间及获批版本；
- 失败、拒绝、过期和未应用结果。

不得把“规则回退成功”显示为“AI 生成成功”。

不得把“可以还原最终有效建议”描述为“可以还原完整原始模型响应”。

## 五、第三部分：测试与安全边界

所有开发和测试使用合成数据、模拟 Transport 和隔离 Repository。

不得：
- 调用真实 AI；
- 修改 Secret；
- 执行共享数据库迁移；
- 导入、重置、审批或执行共享业务数据；
- 删除历史审计记录；
- 删除管理员端依赖的共享业务代码。

运行可能启动 Web 服务或读取工作区的命令之前，先检查其副作用。

最终报告应列出：
1. 删除或保留的模块及依赖理由；
2. 管理员端路由、页面和 API 的验证结果；
3. 审计能力现状与新增内容；
4. 原始模型响应是否持久化；
5. 实际测试命令、结果及未验证事项；
6. 是否访问或修改共享数据库；
7. 是否调用真实 AI；
8. 尚存风险和下一步建议。

先完成只读盘点并给出修改方案，等待确认后再进行破坏性清理。不要一次性大范围删除代码。
